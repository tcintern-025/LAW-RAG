# Pakistan Law Assistant

A grounded, source-cited Q&A assistant built on Retrieval-Augmented Generation (RAG).
It answers questions using only the legal documents it's been given — it names the
document and section behind every answer, and says so plainly when the documents
don't contain enough information to answer.

This repository is also the reference build for **BUILDNEX Digital's** document-intelligence
product line: the same engine, re-pointed at a different set of documents and a different
system prompt, becomes a policy assistant for an insurance agency, a handbook assistant for
an HR team, a support assistant for an e-commerce store, or a contracts assistant for a real
estate brokerage — no rewrite required.

---

## What it does

- Answers questions **strictly from the documents you give it** — no hallucinated law, no
  outside knowledge filling gaps.
- **Cites its sources** — every answer names the source document (and page, where available).
- **Says "I don't know"** when the indexed documents don't cover the question, instead of
  guessing.
- Ships with a **legal disclaimer** on every response: informational/educational use only,
  not a substitute for professional advice.
- Shows the retrieved excerpts alongside the answer (displayed as "Exhibits" in the frontend),
  so a user can verify the answer against the actual source text.

## Who this is for

The demo here is loaded with excerpts from Pakistani law (Constitution, Penal Code, Contract
Act, PECA/cybercrime legislation). The underlying engine is generic — it's a document Q&A
system, not a law-specific one. It's built to be resold, as-is, to any business that has a
pile of dense reference documents and staff or customers who need answers out of them
without reading the whole thing:

- Law firms — case files, contract templates, firm playbooks
- Insurance agencies — policy documents, coverage explainers
- HR teams — employee handbooks, compliance policies, onboarding docs
- E-commerce / SaaS — product docs, return policies, support macros
- Real estate brokerages — contracts, disclosures, local regulations

See **"Reselling this to a new client"** below for exactly what to change.

## How it works

```
documents (PDF/DOCX/TXT)
      │
      ▼
  Load & split into chunks        (app/ingestion)
      │
      ▼
  Embed with Hugging Face model   (app/retrieval/vectorstore.py)
      │
      ▼
  Store in ChromaDB, namespaced   (one isolated collection per CLIENT_ID)
  by client
      │
      ▼
  User asks a question ──► Retriever (MMR) pulls the most relevant,
                            non-redundant chunks
      │
      ▼
  Grounded prompt + retrieved     (app/rag)
  chunks sent to Groq LLM
      │
      ▼
  Answer + cited sources +        returned via FastAPI /ask
  disclaimer
```

## Tech stack

| Layer            | Choice                                   | Why |
|-------------------|-------------------------------------------|-----|
| Backend framework  | FastAPI                                   | Fast, typed, auto-generates API docs |
| RAG orchestration  | LangChain                                 | Standardized loaders/splitters/retrievers |
| Vector store       | ChromaDB                                  | Simple, self-hosted, free |
| Embeddings         | Hugging Face (`all-MiniLM-L6-v2`, local)  | No per-call cost, runs on CPU |
| LLM                | Groq API                                  | Fast inference, low cost |
| Frontend           | React + Vite + Tailwind CSS               | Fast to build, easy to re-skin per client |

## Running it locally

### Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # or your preferred env tool
pip install -r requirements.txt

cp .env.example .env
# edit .env and set GROQ_API_KEY (get one free at console.groq.com)

python -m app.ingestion.build_index   # indexes everything in data/documents
uvicorn app.main:app --reload         # serves on http://localhost:8000
```

Visit `http://localhost:8000/docs` for interactive API docs (auto-generated by FastAPI).

### Frontend

```bash
cd frontend
npm install
cp .env.example .env   # VITE_API_URL defaults to http://localhost:8000, fine for local dev
npm run dev             # serves on http://localhost:5173
```

## Reselling this to a new client

Everything client-specific lives in two places. You do not need to touch any other file.

**1. `backend/app/config.py` (or just set these in `.env`):**

| Variable | What it controls |
|---|---|
| `CLIENT_ID` | Namespaces the vector store — gives this client their own isolated Chroma collection |
| `PRODUCT_NAME` / `PRODUCT_TAGLINE` | Shown in the API docs and can be passed to the frontend |
| `DOMAIN_LABEL` | Used in the system prompt, e.g. "insurance policy documents" instead of "Pakistani law" |
| `DISCLAIMER` | The exact disclaimer text returned with every answer |
| `DOCUMENTS_DIR` | Point this at the new client's document folder |

**2. `backend/app/rag/prompts.py`** — only touch this if the new domain needs different
behavioral rules (for example, an HR assistant might need "escalate anything about
termination to a human" instead of the "no legal conclusions" rule used here).

**3. Swap the documents** in `data/documents/`, then re-run:

```bash
python -m app.ingestion.build_index
```

**4. Frontend branding** — update `PRODUCT_NAME` / `TAGLINE` in `frontend/src/App.jsx` and,
if desired, the color tokens in `frontend/tailwind.config.js`.

That's the entire reselling workflow: new `CLIENT_ID`, new documents, one ingestion run,
a few lines of copy. No architecture changes.

## Deployment

### Backend (Render / Railway / Koyeb — all have free tiers)

The included `Dockerfile` builds the vector index at image build time so the container
serves immediately on boot.

1. Push this repo to GitHub.
2. Create a new Web Service on your chosen platform, pointed at the `backend/` directory
   (or the repo root with the Dockerfile path set to `backend/Dockerfile`, depending on the
   platform).
3. Set the environment variables from `.env.example` in the platform's dashboard
   (at minimum: `GROQ_API_KEY`).
4. Deploy. Note the live URL, e.g. `https://your-app.onrender.com`.

If a client's documents change often, move the `RUN python -m app.ingestion.build_index`
line out of the Dockerfile and into a separate startup script or scheduled job instead, so
you're not rebuilding the whole image for a document update.

### Frontend

Deploy `frontend/` to Vercel or Netlify (both have generous free tiers for a project this
size). Set the `VITE_API_URL` environment variable in the hosting platform's dashboard to
your deployed backend URL from the step above, then redeploy.

## Project structure

```
backend/
  app/
    config.py          ← client/branding config (edit this to resell)
    main.py             ← FastAPI app: /ask, /health, /sources
    schemas.py           ← request/response models
    ingestion/
      loader.py           ← loads PDFs/DOCX/TXT from a folder
      splitter.py          ← chunking strategy
      build_index.py        ← run this to (re)index documents
    retrieval/
      vectorstore.py        ← Chroma, namespaced by CLIENT_ID
      retriever.py           ← MMR-based retrieval
    rag/
      prompts.py              ← system prompt / grounding rules (edit this to resell)
      chain.py                  ← retrieve → prompt → Groq → structured answer
  data/documents/          ← sample legal document excerpts (replace with real docs)
  Dockerfile
  requirements.txt
  .env.example

frontend/
  src/
    App.jsx               ← main chat UI
    api.js                 ← backend API client
    components/              ← Header, ChatMessage, ChatInput, ExhibitList
  .env.example
```

## Important note on the sample documents

The files in `backend/data/documents/` are **condensed, illustrative excerpts** written for
demo purposes — not the official, complete legal text. Before using this for anything beyond
a demo, replace them with the full official documents (Constitution of Pakistan, Pakistan
Penal Code, Contract Act, PECA) from an authoritative source, or with a client's real
documents when reselling.
